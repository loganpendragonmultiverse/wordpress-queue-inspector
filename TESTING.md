# Testing and known limits

Run `python3 -m unittest discover -s tests -v`. The local suite covers overdue and repeated failures, old and changed claim evidence, disabled internal cron interpretation, partial disappearance, recorded completion, ambiguous recurring fingerprints, equivalent timezone offsets, shared age/state/group filtering, strict privacy field rejection, site/time/count rejection, HTML and Markdown escaping, incident hash tamper detection, 300-job input, browser page 4, chronological log view, hostile Host header, interrupted import, multi-capture direction, notes, and ZIP backup/restore. CLI smoke uses the sample snapshots. On Linux with PHP, `tests/exporter_failures.php` simulates failed action/log counts and page reads plus unreadable WP-Cron and verifies none are marked complete.

Disposable integration on 2026-11-02: WordPress 7.1.4, PHP 8.3.36, Action Scheduler 4.2.0, MariaDB 11.8.9, WP-CLI in an isolated Docker fixture. A real export had 4 actions, 10 cron events and 4 logs, with complete counts. It detected one overdue pending action, two failed actions on a hook and an absent registered cron callback. A 514-action export crossed the 500-row pagination boundary, reconciled counts, and omitted a sentinel action argument, fixture email and server path. After the claim addition, another real export had 514 actions, 10 cron and 514 logs with complete counts and no sentinel data; an intentionally old fixture claim was collected as an opaque ID and creation time and produced `old-claim` evidence. A controlled before/after DB read showed unchanged action status counts, log count and WP-Cron option digest across one export; this is a fixture observation, not a guarantee about WordPress bootstrap on another site. A second capture after the fixture action's recorded completion showed pending → complete. No client site was used. `--hook=init` is required for WP-CLI `eval-file`; `after_wp_load` did not execute the file. PHP 8.2.35 lint passed.

A synthetic Python 3.12.14 in-memory 100,000-action validate/findings/compare run took 1.426 seconds and peaked at 116,384 KiB RSS. `python3 tests/benchmark_100k.py` loaded a 12,289,218-byte JSON snapshot into the local server in 0.321 seconds, returned page 1,000 in 0.271 seconds and an exact-ID search in 0.263 seconds, with 89,460 KiB server RSS. Host: Linux x86_64 cloud container, 5 visible AMD EPYC 9V74 vCPUs, 16 GiB memory limit. These are fixture measurements; real logs, hook diversity, browser rendering and other hardware may differ.

Chromium 2026-11-02 smoke (`node tests/browser_smoke.cjs` with Playwright and Chromium already installed): selected action 0 on page 1 and action 300 on page 4, then searched and paged; both selections and the count persisted. The browser also switched to the latest of three captures, compared middle to latest, rejected reverse chronology, saved an operator note and included it in the report. HTML, Markdown and JSON report routes share the core report function. A sample browser screenshot is in `screenshots/incident.png`.

Unverified: final independent reviewer signoff, external platform installation, assistive technology audit, 100,000-job exporter and native browser rendering, and independent comparison with WordPress admin tools. Gold remains pending until the applicable release gates pass. The exporter relies on Action Scheduler's default tables and does not collect custom data stores. Log messages are intentionally omitted, limiting failure diagnosis. Source rows changing during capture can make pagination reconciliation partial.
